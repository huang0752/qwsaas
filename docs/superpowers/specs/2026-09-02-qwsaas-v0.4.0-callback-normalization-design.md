# qwsaas v0.4.0 Callback Normalization Design

**Status:** Approved design draft, pending written-spec review

**Scope:** `qwsaas` SDK callback normalization only

**Target release:** `v0.4.0`; implementation remains `0.4.0rcN` until every real gate passes

**Protocol source:** [企微协议 SAAS](https://wework.apifox.cn/)

## 1. Goal

Rebuild callback normalization around the documented Juhe/QW SaaS protocol, remove ambiguous `v0.3.5` abstractions, correctly preserve non-message events, produce account-scoped conversation identity, and require real desktop, mobile, API, batch, state, and multi-account callback evidence before the final `v0.4.0` release.

This is a breaking release, not a compatibility patch. It does not preserve incorrect callback field aliases as the primary API.

## 2. Evidence Policy

Every callback rule belongs to exactly one evidence class:

1. **Apifox documented**: explicitly stated by the public protocol documentation.
2. **SDK transport contract**: an input wrapper created or consumed by `qwsaas`, such as its WebSocket callback envelope.
3. **Real callback verified**: behavior established through redacted callbacks captured from real desktop, mobile, API, group, state, batch, and multi-account scenarios.

Documentation examples do not prove undocumented field semantics. In particular:

- Apifox includes `send_flag` in its 11010 example but does not define its values.
- Apifox lists `NotifyTypeBatchNewMsg = 11013` but does not publish the shape of its `data` payload.
- Apifox defines the `S:<user-id>` and `R:<room-id>` conversation ID formats but does not explicitly say whether a private callback's peer is selected from `sender` or `receiver`.
- Apifox send examples return `data.msg_data`, but do not promise how every returned identifier relates to a later callback.

These behaviors must not become release contracts until the real callback matrix confirms them.

## 3. Documented Protocol Facts

The public design relies on these documented facts:

- The HTTP callback event is a top-level object containing `guid`, `notify_type`, and `data`.
- `NotifyTypeNewMsg` is 11010 and `NotifyTypeBatchNewMsg` is 11013.
- `MsgType` defines 0, 1-16, 1011, and 1012; 1 is revoke, 2 is text, and 1012 is read report.
- `MessageFlagField` is a bit field and must be decoded with bitwise operations.
- A private send target has the form `S:<user-id>` and a room target has the form `R:<room-id>`.
- `referid == 0` identifies an original message. A non-zero `referid` identifies a change such as a read or revoke callback and refers to a message ID.
- `id` and `seq` are unique only within a user scope; `appinfo` is globally unique.
- `quote_appinfo` relates quoted content to the quoted message's `appinfo`.
- A 11003 login callback exposes `data.user_id`.
- `/sync/sync_msg` is deprecated, rate-limited, and intended only for missing-message recovery.
- Documented send responses may return `data.msg_data` containing `id`, `seq`, `appinfo`, `sender`, `receiver`, `roomid`, `sendtime`, `flag`, and `asid`.

## 4. Architecture

The new design separates seven responsibilities:

1. Extract a protocol event from an official HTTP payload or an SDK transport wrapper.
2. Dispatch only confirmed message notify types to message parsing.
3. Preserve the documented protocol fields without renaming their meaning.
4. Normalize protocol identifiers before comparing them or constructing conversation IDs.
5. Derive account-relative identity in a separate, repeatable phase using a known current-account context and verified invariants.
6. Parse live 11010, verified 11013, and `/sync/sync_msg` records through separate source adapters that share one single-message protocol parser.
7. Produce a logical business-message key from documented message identifiers, never from callback fingerprints.
8. Parse outbound send results separately and correlate them to callbacks only with documented strong identifiers.
9. Make every callback model safe against accidental `repr` logging and provide one redacted logging representation.

The current `callbacks.py` facade remains the public import location. Implementation responsibilities move into focused modules:

```text
src/qwsaas/
├── callbacks.py
├── callback_models.py
├── callback_envelope.py
├── callback_messages.py
├── sync_messages.py
├── callback_identity.py
├── callback_attachments.py
├── callback_redaction.py
├── message_results.py
├── enums.py
├── exceptions.py
└── __init__.py
```

- `callbacks.py`: public entry points and re-exports.
- `callback_models.py`: protocol fields, pure parsed models, normalized identity models, parse issues, and sent-message references.
- `callback_envelope.py`: official HTTP and SDK WebSocket envelope extraction.
- `callback_messages.py`: 11010/11013 dispatch and message, quote, flag, and state parsing.
- `sync_messages.py`: `/sync/sync_msg` item parsing without manufacturing a callback notify type.
- `callback_identity.py`: ID normalization plus account-relative direction, peer, and conversation calculation.
- `callback_attachments.py`: zero-or-more callback attachment metadata extraction.
- `callback_redaction.py`: shared redacted `repr` and `to_safe_dict()` support.
- `message_results.py`: documented `data.msg_data` extraction and strong callback correlation.
- `enums.py`: Apifox enums plus clearly named SDK normalization enums.
- `exceptions.py`: callback structure errors.
- `__init__.py`: `v0.4.0` public exports.

## 5. Envelope Parsing

### 5.1 Official protocol

The official HTTP shape is:

```json
{
  "guid": "instance-guid",
  "notify_type": 11010,
  "data": {}
}
```

If the input object's top level contains a valid `notify_type`, the top-level object is the event. Its `data` must not be mistaken for a nested event.

### 5.2 SDK transport wrappers

The SDK may separately support wrappers already used by its WebSocket transport:

```json
{"type": "callback", "event_id": "evt-1", "event": {}}
```

The `event` value may be an object or a JSON-encoded object when that behavior is confirmed by the SDK transport contract. A `data`-wrapped event may also be supported when the wrapper itself is confirmed by an SDK fixture and the nested object contains `notify_type`.

These wrappers must be documented as SDK transport formats, not as upstream Apifox formats.

### 5.3 Selection and conflict rules

Extraction order is:

1. A top-level object that contains `notify_type`.
2. A confirmed `event` wrapper.
3. A confirmed `data` wrapper whose nested value is itself an event.

Presence at the top level is authoritative: `notify_type` must be a non-negative JSON integer and must not be a boolean. If the field exists with any other type or value, parsing fails immediately. The parser must not fall through to an inner `event` or `data` candidate and thereby hide a damaged official callback. Unknown non-negative integer values remain valid non-message events.

The parser does not recursively search arbitrary nested dictionaries. If the top level has no `notify_type` and multiple wrapper candidates contain conflicting events, strict parsing raises a structure error instead of silently selecting one.

### 5.4 Strict and tolerant entry points

```python
def parse_callback_envelope(
    payload: Mapping[str, Any],
) -> JuheCallbackEnvelope:
    """Purely parse protocol and transport structure or raise."""


def try_parse_callback_envelope(
    payload: Mapping[str, Any],
) -> JuheCallbackEnvelope | None:
    """Return None only for an invalid callback structure."""


def normalize_callback_identity(
    envelope: JuheCallbackEnvelope,
    *,
    current_account_id: object,
) -> JuheNormalizedCallbackEnvelope:
    """Add account-relative identity without reparsing the payload."""


def parse_and_normalize_callback(
    payload: Mapping[str, Any],
    *,
    current_account_id: object,
) -> JuheNormalizedCallbackEnvelope:
    """Convenience composition of parse and identity normalization."""
```

`parse_callback_envelope()` is deterministic for a given payload and never depends on account cache state. If identity arrives later from a 11003 callback or host persistence, callers can run `normalize_callback_identity()` on the already parsed envelope. The composition helper exists for callers that already have the account identity.

Valid non-message events always return an envelope.

## 6. Event Dispatch

Only message notify types established by documentation and verified payload fixtures may create `JuheCallbackMessage` objects.

- 11010 is a documented message event.
- 11013 is a documented batch-message enum, but its payload shape remains release-blocked until a real sample is captured.
- All other known notify types return `messages=()` and preserve the event.
- Unknown integer notify types also return `messages=()` and preserve the event.
- A malformed payload for a confirmed message notify type is a parse error, not an empty or fake text message.

The final 11013 parser must implement the exact real structure recorded in the approved fixture. It must not assume that `data` is a list merely because the event name contains `Batch`.

### 6.1 Separate message sources

Live 11010, verified 11013, and `/sync/sync_msg` are different sources:

```python
def parse_protocol_message(
    raw_message: Mapping[str, Any],
    *,
    source: MessageSource,
    source_event_key: str,
    item_index: int,
) -> JuheCallbackMessage:
    """Shared parser for one protocol message record."""


def parse_sync_messages(
    raw_messages: Sequence[Mapping[str, Any]],
    *,
    sync_page_key: str,
) -> tuple[JuheCallbackMessage, ...]:
    """Parse explicit sync records without creating a callback envelope."""
```

- A 11010 adapter passes its single documented `data` record to `parse_protocol_message()` with source `REALTIME_11010`.
- The 11013 adapter is implemented only after its complete real structure is approved and passes each actual item to the same parser with source `REALTIME_11013`.
- `parse_sync_messages()` accepts an explicitly supplied sequence of sync records. It does not guess where a currently undocumented sync response stores that sequence.
- Sync messages use source `SYNC_MSG`, a sync-page fingerprint, and their page index. They are never wrapped in a synthetic event with `notify_type=11013`.
- If a future real `/sync/sync_msg` response envelope is approved, a separate response adapter may extract its records and cursor before calling `parse_sync_messages()`.

Super Mate's current recovery implementation and database records are consumer behavior, not evidence for upstream 11013 or sync-response protocol shape.

## 7. Public Models

### 7.1 Protocol fields

Protocol fields retain Apifox names, original scalar types, and meanings. `ProtocolIdValue` is `str | int | float | bool | None`; accepting the type in the protocol model does not mean it is a valid normalized ID.

```python
@dataclass(frozen=True, repr=False)
class JuheMessageProtocolFields:
    id: ProtocolIdValue = field(repr=False)
    seq: ProtocolIdValue = field(repr=False)
    appinfo: ProtocolIdValue = field(repr=False)
    sender: ProtocolIdValue = field(repr=False)
    receiver: ProtocolIdValue = field(repr=False)
    roomid: ProtocolIdValue = field(repr=False)
    sendtime: int | None
    sender_name: str | None = field(repr=False)
    content_type: int | None
    referid: ProtocolIdValue = field(repr=False)
    flag: int | None
    content: Any = field(repr=False)
    at_list: tuple[str, ...] = field(repr=False)
    quote_content: str | None = field(repr=False)
    quote_appinfo: ProtocolIdValue = field(repr=False)
    send_flag: int | None
    msg_type: int | None
    asid: ProtocolIdValue = field(repr=False)
```

The parser records actual upstream scalar types here. Normalized values are produced separately. Missing or invalid optional fields produce a non-sensitive parse issue. The original message remains available in `raw_message`.

### 7.2 Pure parsed message

```python
@dataclass(frozen=True, repr=False)
class JuheCallbackMessage:
    protocol: JuheMessageProtocolFields = field(repr=False)
    text: str = field(repr=False)
    sent_at: datetime | None
    message_kind: MsgType | None
    message_relation: MessageRelation
    state_kinds: frozenset[MessageStateKind]
    flags: frozenset[MessageFlagField]
    unknown_flag_bits: int
    callback_message_key: str
    batch_index: int
    source: MessageSource
    attachments: tuple[JuheAttachment, ...] = field(repr=False)
    parse_issues: tuple[JuheCallbackParseIssue, ...]
    raw_message: dict[str, Any] = field(repr=False)
    raw_event: dict[str, Any] = field(repr=False)
```

`MessageRelation` is `ORIGINAL`, `SUBSIDIARY`, or `UNKNOWN`. A missing or malformed `referid` is not silently treated as subsidiary.

### 7.3 Identity-normalized message

```python
@dataclass(frozen=True, repr=False)
class JuheNormalizedCallbackMessage:
    source: JuheCallbackMessage = field(repr=False)
    sender_id: str | None = field(repr=False)
    receiver_id: str | None = field(repr=False)
    room_id: str | None = field(repr=False)
    current_account_id: str | None = field(repr=False)
    conversation_kind: ConversationKind
    direction: MessageDirection
    contact_id: str | None = field(repr=False)
    provider_conversation_id: str | None = field(repr=False)
    account_conversation_key: str | None = field(repr=False)
    identity_failures: frozenset[IdentityFailureReason]

    @property
    def is_self_authored(self) -> bool | None:
        if self.direction is MessageDirection.OUTBOUND:
            return True
        if self.direction is MessageDirection.INBOUND:
            return False
        return None
```

`is_self_authored` is a derived three-state property, not stored duplicated state. `is_self_echo` does not exist in the `v0.4.0` model. An account-authored message is not automatically a duplicate API echo.

`IdentityFailureReason` includes at least `CURRENT_ACCOUNT_MISSING`, `CURRENT_ACCOUNT_INVALID`, `SENDER_INVALID`, `RECEIVER_INVALID`, `ROOM_ID_INVALID`, `ACCOUNT_NOT_PARTICIPANT`, `DIRECT_PEER_MISSING`, and `ROOM_DIRECTION_UNVERIFIED`. Multiple reasons may coexist and are returned as a set; callers do not have to infer failure from a collection of `None` fields.

### 7.5 Safe representation

Every callback-related dataclass uses `repr=False`. Every secret-, identity-, content-, URL-, or raw-payload-bearing field also uses `field(repr=False)` so that a future accidental return to generated repr remains fail-closed.

All callback models implement the same safe interface:

```python
class SafeCallbackRepr:
    def to_safe_dict(self) -> dict[str, JSONSafeValue]:
        """Return structural diagnostics without content, identity, or secrets."""

    def __repr__(self) -> str:
        return f"{type(self).__name__}({self.to_safe_dict()!r})"
```

Safe dictionaries may contain event/message types, counts, direction, conversation kind, attachment kinds, sizes, MIME types, parse issue codes, and booleans indicating whether a field exists. They must not contain message content, names, IDs, filenames, raw payloads, URLs, headers, cookies, `aes_key`, `auth_key`, `base_request`, or signed query parameters.

`to_safe_dict()` is the only supported callback logging representation. It is not a lossless serializer. Lossless access remains available through explicitly named protocol and raw fields, all excluded from repr.

## 8. Message Type, Flags, and State

`msg_type` is parsed strictly from the documented `MsgType` enum:

- Missing or non-integer: `message_kind=None` plus a malformed-field issue.
- Recognized integer: the matching `MsgType`.
- Unknown integer: retain the raw integer in `protocol.msg_type`, set `message_kind=None`, and add an unsupported-type issue.

There is no default text type. Plain-text fallback is permitted only for `MsgTypeText == 2`.

`flag` is decoded with bitwise operations into a set of known `MessageFlagField` members while preserving the raw integer. Bits not covered by the documented enum are returned through `unknown_flag_bits` and a parse issue.

State rules are limited to documented facts:

- Normalized `referid == "0"` means `MessageRelation.ORIGINAL`.
- A valid non-zero normalized `referid` means `MessageRelation.SUBSIDIARY` and refers to a message ID.
- Missing, zero-like-but-invalid, wrongly prefixed, boolean, floating-point, or otherwise malformed `referid` means `MessageRelation.UNKNOWN` plus a parse issue.
- `MsgTypeRevoke == 1` means revoke.
- `MsgTypeSystem == 1011` means system message and must never be classified as revoke merely because `referid` is non-zero.
- `MsgTypeReadReport == 1012` means read report.
- Documented flag bits contribute only their named meanings.
- Every recognized signal contributes to `state_kinds: frozenset[MessageStateKind]`; no single-state priority is imposed.
- If no state is recognized, `state_kinds` contains only `MessageStateKind.UNKNOWN`.
- If multiple recognized signals coexist, all are retained. The SDK does not call them conflicting unless Apifox or real verified evidence establishes that the combination is impossible.
- Content text is never used to guess a state.

## 9. Identity and Conversation Scope

### 9.1 ID normalization

Identity comparison and target construction operate only on normalized IDs. Raw values remain unchanged in `JuheMessageProtocolFields` and `raw_message`.

Three typed normalization functions are public and independently tested:

```python
normalize_account_id(value: object) -> str | None
normalize_user_id(value: object) -> str | None
normalize_room_id(value: object) -> str | None
```

Rules are deterministic:

- `bool` is always invalid even though Python treats it as an integer.
- A positive `int` becomes its base-10 string.
- `float` is rejected; `0.0` is treated as a zero-like missing value, while every other float produces an invalid-ID issue.
- A string is trimmed at both ends but otherwise retains its digits and leading zeroes.
- Empty strings and case-insensitive `"0"`, `"0.0"`, `"null"`, and `"none"` become `None`.
- A user or account ID may contain no prefix or exactly one `S:` prefix; the prefix is removed for normalized storage.
- A room ID may contain no prefix or exactly one `R:` prefix; the prefix is removed for normalized storage.
- A wrong prefix and repeated prefixes such as `S:S:123` or `R:R:123` are invalid and produce an issue instead of being silently stripped.
- Target construction adds exactly one `S:` or `R:` prefix to a normalized unprefixed ID.

The normalizer does not convert arbitrary strings to integers and does not use Python truthiness.

### 9.2 Evidence prerequisite

The identity algorithm becomes a release contract only after the real callback matrix confirms the relationship among 11003 `user_id`, message `sender`, message `receiver`, `roomid`, and the actual user action.

The expected private-message invariant to validate is:

```python
if sender == current_account_id:
    provider_conversation_id = f"S:{receiver}"
elif receiver == current_account_id:
    provider_conversation_id = f"S:{sender}"
else:
    provider_conversation_id = None
```

Private direction is expected to follow the same verified account relationship:

- sender equals current account: outbound.
- receiver equals current account: inbound.
- missing or inconsistent identity: unknown.

Room identity and room direction are separate decisions:

- A valid non-zero normalized `roomid` establishes `ConversationKind.ROOM` and `R:<room-id>`.
- It does not by itself establish direction.
- Desktop, mobile, API, and inbound room fixtures must produce an explicit room truth table covering `sender`, `receiver`, current account ID, room ID, and `send_flag`.
- The room direction algorithm is implemented only from that approved truth table; until then it returns `MessageDirection.UNKNOWN`.

If real evidence contradicts either expected private invariant or the proposed room truth table, implementation stops and the design is revised before release. `send_flag` is always preserved but is not assigned a meaning until desktop, mobile, and API evidence establishes one.

### 9.3 Conversation kind and scope

```text
provider_conversation_id = S:<contact-id> or R:<room-id>
account_conversation_key = juhe:<current-account-id>:<provider-conversation-id>
```

The provider ID is suitable for Juhe message APIs. The SDK application key scopes that provider ID only by normalized current account ID. Without a known current account ID, the SDK does not invent an application conversation key.

Host-specific connection, tenant, deployment, or instance namespaces are not added by `qwsaas`. A host such as Super Mate may prepend or wrap the SDK's account-scoped key when its own persistence model requires another namespace.

`conversation_kind` is always returned as `DIRECT`, `ROOM`, or `UNKNOWN`. Callers do not need to reverse-engineer it from the target prefix. A valid non-zero normalized room ID yields `ROOM`; a verified private peer relationship yields `DIRECT`; otherwise it is `UNKNOWN`.

`guid` remains an instance identifier and is preserved separately. It is not silently treated as a stable account ID.

### 9.4 Boolean inputs

Boolean-like upstream fields use a strict converter. Actual booleans and documented numeric values are accepted. Strings are parsed only through an explicit allow-list such as `"0"`, `"1"`, `"false"`, and `"true"`; Python string truthiness is never used. A non-zero `roomid` remains the primary documented room fact.

## 10. Message and Event Identifiers

The SDK does not merge documented identifiers into a single ambiguous `message_id`:

- `protocol.id`: local/user-scoped message ID.
- `protocol.seq`: local/user-scoped sequence.
- `protocol.appinfo`: globally unique message ID.
- `wrapper_event_id`: SDK transport event ID, when present.
- `envelope_event_key`: SDK-generated fingerprint for one complete callback envelope.
- `callback_message_key`: SDK-generated fingerprint for one message item inside the envelope.

`envelope_event_key` is calculated as follows:

1. If a confirmed SDK wrapper event ID exists, hash a canonical object containing `guid` and the wrapper event ID.
2. Otherwise hash a canonical object containing `guid`, `notify_type`, and the complete raw event `data`.

For each parsed message, `callback_message_key` hashes this canonical object:

```json
{
  "envelope_event_key": "...",
  "batch_index": 0,
  "raw_message": {}
}
```

Canonical JSON uses UTF-8, sorted object keys, and fixed separators, then SHA-256. `batch_index` is zero for a single 11010 message and is the exact item position for an approved 11013 batch shape. Messages within one batch therefore have distinct keys, while an exact replay of the same envelope produces the same per-message keys.

Both generated keys are payload fingerprints, not provider-guaranteed idempotency keys. They are not guaranteed to survive an upstream wrapper event ID change, object re-encoding, field addition, array reorder, regenerated signed URL, or any other payload mutation. Durable logical message deduplication uses documented identifiers and explicit scope, not these fingerprints alone.

Logical message correlation uses `appinfo` first. `id` or `seq` may be used only with an explicit current-account scope.

### 10.1 Logical business-message key

The SDK exposes one result-bearing method:

```python
@dataclass(frozen=True, repr=False)
class JuheLogicalMessageKey:
    value: str | None = field(repr=False)
    source: LogicalMessageKeySource | None
    failure_reason: LogicalMessageKeyFailure | None


def logical_message_key(
    message: JuheCallbackMessage | JuheMessageProtocolFields,
    *,
    current_account_id: object | None = None,
) -> JuheLogicalMessageKey:
    ...
```

Priority is exact:

1. A valid non-empty `appinfo` produces a global logical key and needs no account context.
2. Otherwise, a valid normalized current account plus valid `id` produces an account-scoped local-ID key.
3. Otherwise, a valid normalized current account plus valid `seq` produces an account-scoped sequence key.
4. Otherwise no value is returned and `failure_reason` states whether account identity or every documented message identifier was missing or invalid.

The string value hashes a canonical namespace, scope, identifier kind, and identifier value with SHA-256 so logs and persistence do not expose raw IDs. The key source remains explicit as `APPINFO`, `ACCOUNT_ID`, or `ACCOUNT_SEQUENCE`.

`envelope_event_key`, `callback_message_key`, and sync-page fingerprints are never accepted as fallbacks for this method and must not be documented as persistent business-message keys.

## 11. Outbound Result Correlation

Documented message-send responses may expose `data.msg_data`. The SDK adds:

```python
@dataclass(frozen=True, repr=False)
class JuheSentMessageRef:
    id: ProtocolIdValue = field(repr=False)
    seq: ProtocolIdValue = field(repr=False)
    appinfo: ProtocolIdValue = field(repr=False)
    sender: ProtocolIdValue = field(repr=False)
    receiver: ProtocolIdValue = field(repr=False)
    roomid: ProtocolIdValue = field(repr=False)
    sendtime: int | None
    flag: int | None
    asid: ProtocolIdValue = field(repr=False)


def parse_sent_message_ref(
    response: Mapping[str, Any],
) -> JuheSentMessageRef | None:
    ...
```

Strong callback correlation requires equivalent non-empty `appinfo`, because Apifox defines it as globally unique. Official and approved observed evidence shows that a send response may contain a canonical Base64 UTF-8 representation while the callback contains its decoded value. The SDK compares candidate sets containing the untouched original and at most one strict, canonical standard-Base64 UTF-8 decode; invalid encodings add no candidate and never raise. The SDK does not claim an API-origin match from `send_flag`, sender identity, timestamp proximity, text equality, `id` alone, or `seq` alone.

If a real endpoint fails to return the callback's `appinfo`, correlation for that endpoint remains unknown unless the documentation or approved real evidence establishes another strong key.

## 12. Attachment Model

Attachment extraction remains type-directed and preserves documented callback parameters required for CDN resolution. A message exposes `attachments: tuple[JuheAttachment, ...]`, not a single optional attachment, so mixed and merged messages do not require another public-model break.

```python
@dataclass(frozen=True, repr=False)
class JuheAttachment:
    kind: AttachmentKind
    file_name: str | None = field(repr=False)
    file_id: str | None = field(repr=False)
    file_key: str | None = field(repr=False)
    file_size: int | None
    file_md5: str | None = field(repr=False)
    aes_key: str | None = field(repr=False)
    auth_key: str | None = field(repr=False)
    auth_cookies: str | None = field(repr=False)
    download_url: str | None = field(repr=False)
    mime_type: str | None
    is_hd: bool | None
    base_request: dict[str, Any] | None = field(repr=False)
    raw_payload: dict[str, Any] = field(repr=False)
```

The existing download resolver remains responsible for qpic, C2C, private WeChat, and big-file routing. Callback normalization only extracts and preserves the inputs. It does not download data while parsing.

Known single-media fixtures produce a one-item tuple. Empty or non-media messages produce an empty tuple. Mixed and merge extraction is implemented only from real approved fixtures; unsupported nested media remains in raw data and produces an issue rather than being silently discarded or flattened into one attachment.

## 13. Error and Issue Model

Envelope structure errors raise `QwSaasCallbackParseError` with:

```python
code: CallbackParseErrorCode
path: str
notify_type: int | None
message: str
```

Structural error codes cover invalid input type, missing or invalid notify type, conflicting event candidates, invalid confirmed message payload, and invalid confirmed batch payload.

Field-level problems use `JuheCallbackParseIssue` and do not discard the message. Issues contain a code, field path, and actual value type. They do not copy secret-bearing raw values into logs or exception strings.

`raw_event`, `raw_message`, `raw_envelope`, protocol content, identity fields, and attachment secrets remain explicitly accessible to the caller but are excluded from every default repr. Library logs use only `to_safe_dict()`. Tests assert that `repr()` of every public callback model cannot contain fixture IDs, content, names, filenames, URLs, cookies, keys, `base_request`, or raw payload fragments.

Fixtures must be copied from real callbacks and then consistently redacted. Stable replacement IDs must preserve equality relationships across related fixtures. Secrets, cookies, signed query strings, media keys, personal names, and real account identifiers must not be committed.

Each fixture records only non-sensitive provenance metadata: source device category, inbound/outbound user action, API endpoint when applicable, and capture date.

Private and room evidence produce separate truth tables. The room table explicitly records current account ID, sender, receiver, room ID, `send_flag`, source device, user action, and resulting direction; private receiver rules are never reused for rooms without that evidence.

Fixture safety is enforced by `scripts/check_callback_fixtures.py`, not only manual review. It recursively rejects:

- Values under `aes_key`, `auth_key`, cookie, authorization, and secret-bearing `base_request` leaves unless the value is the exact token `REDACTED`.
- HTTP query values other than the exact token `REDACTED`; query parameter names and structure may remain.
- Identity and name values outside the fixture's declared placeholder allow-list.
- Known WeChat/WeCom ID patterns matching `(?:168|788|10)\d{8,}` unless explicitly present in an Apifox public-example fixture.
- Strings of at least 24 characters with Shannon entropy of at least 4.0 bits per character unless the JSON path is explicitly allow-listed as public fixture data.
- Raw authorization headers, signed URL parameters, and unapproved external hosts.

The scanner validates a per-sequence placeholder manifest so equality relationships remain testable. Stable placeholders such as `ACCOUNT_A`, `CONTACT_A`, `ROOM_A`, and `APPINFO_A` replace real values consistently. Apifox public-example fixtures and real-callback fixtures are scanned under separate policies because public documentation may contain non-secret example identifiers.

## 16. Breaking Changes and Migration

The migration guide explicitly maps:

| `v0.3.5` | `v0.4.0` |
| --- | --- |
| `message_id` | `protocol.id`, `protocol.seq`, or `protocol.appinfo` according to required scope |
| `message_type` with default 2 | `protocol.msg_type` plus `message_kind` without a default |
| `conversation_id` | `provider_conversation_id` |
| `is_group` | `conversation_kind: DIRECT | ROOM | UNKNOWN` |
| `is_self_echo` | removed; use direction, three-state `is_self_authored`, or explicit send-result correlation |
| `is_original: bool` | `message_relation: ORIGINAL | SUBSIDIARY | UNKNOWN` |
| `state_kind` | `state_kinds: frozenset[MessageStateKind]` |
| One callback key on every message | envelope-level `envelope_event_key` plus per-item `callback_message_key` |
| Flat `seq/appinfo/referid` | `protocol.seq/appinfo/referid` |
| Flat attachment fields | `attachments: tuple[JuheAttachment, ...]` |
| Invalid envelope returning `None` | strict exception or `try_parse_callback_envelope()` |
| Parsing coupled to account context | pure `parse_callback_envelope()` followed by `normalize_callback_identity()` |

No legacy alias may silently preserve an incorrect semantic. Raw protocol data remains available for controlled host migrations.

The migration guide must also state that upgrading the SDK does not repair previously split or merged host database conversations.

- Git diff contains no unrelated changes or real callback secrets.
- The final tag points to the exact accepted commit.

Before every mandatory real gate passes, package metadata may advance only through PEP 440 release candidates such as `0.4.0rc1`. Documentation and release notes must label the implementation RC, and no final `v0.4.0` tag or final package may be created.

If any mandatory real evidence is missing or contradicts the expected identity invariant, the release remains a candidate and must not receive the final `v0.4.0` tag. Only complete raw callbacks captured for the named matrix may establish `receiver`, `send_flag`, 11013, and room-direction behavior. Super Mate code, tests, transformed payloads, and existing database rows are never protocol truth.

## 19. Out of Scope

- Migrating Super Mate or any other host application's database.
- Providing `v0.3.5` aliases such as `message_id`, `conversation_id`, or `is_self_echo`.
- Automatically merging historically split host conversations.
- Changing host-specific automation, reply, or human-takeover policy.
- Treating deprecated `/sync/sync_msg` as a normal ingestion mechanism.
- Fully typed models for every non-message notify payload.
- Inferring undocumented `send_flag` semantics.
- Publishing, tagging, pushing, or updating downstream dependencies during design and planning.
